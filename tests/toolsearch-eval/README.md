# Tool-selection eval (progressive disclosure)

Measures whether the token-optimised toolset (`minimal` + `find_tool`/`call_tool`,
see `toolsearch.py`) selects tools as well as loading the full 92-tool set — the
bar being **no regression vs. no optimization at all**.

## Why this exists

MCP tool definitions load into the model's context on every request. We cut the
always-on cost ~60% by serving 28 hot-core tools directly and exposing the other
64 through two meta-tools (`find_tool` ranks the full library; `call_tool`
dispatches any tool by name). The risk of any such scheme is that the retriever
fails to surface the right long-tail tool, so the agent can't route to it. This
eval quantifies that risk.

## Methodology

Follows the 2026 agent-eval consensus — compare the three tool-selection
strategies the literature names and measure **retrieval recall separately from
routing**, because a retriever that can't surface the right tool (low context
recall) forces wrong calls:

| literature term | ours |
|---|---|
| "all" (load everything) | `full` — 92 tools loaded directly |
| "domain / curated" | `minimal-core` — 28 hot-core only, no meta-tools |
| "retrieval" (RAG-over-tools) | `minimal+search` — 28 core + `find_tool`/`call_tool` (shipped) |

`cases.json` holds 40 natural-language tasks with deterministic gold labels
(+ acceptable alternates). No LLM judge is needed for these metrics.

Metrics:
- **Coverage (context recall)** — is the gold tool reachable at all in this
  strategy? For `minimal+search`, any tool in the library is reachable via
  `call_tool`, so coverage is a hard 100%.
- **`find_tool` recall@k** — for long-tail tasks, is the gold tool in the top-k
  returned. **recall@8/@10 is the parity metric**: `find_tool` returns a
  candidate set and the model makes the final pick from it, exactly as it would
  from the full 92 — but with fewer distractors, which the research shows
  *improves* selection. Gold in that set ⇒ routes at least as well as `full`.
- **Routing precision@1** — fraction of all tasks where the correct tool is the
  top available choice (core: directly loaded; long-tail: `find_tool` top-1).

## Two datasets

- `cases.json` — 40 hand-written cases (author-labeled).
- `generated_cases.json` — **191 cases across 91 tools, generated by a separate
  agent** that only saw the tool catalog, phrased by intent in varied/slangy
  language ("shut this group up", "that guy from work"). Independent of the alias
  map, so it is the honest, overfitting-resistant measurement.

## Lexical-retriever results (2026-07-17, deployed code)

| metric | curated 40 | **generated 191 (independent)** |
|---|---|---|
| Coverage (minimal+search) | 100% | 100% |
| Coverage (old minimal-core) | 35% | 32% |
| find_tool recall@1 | 92% | 48% |
| find_tool recall@5 | 100% | 74% |
| find_tool recall@8 | 100% | 75% |
| MRR | 0.962 | 0.600 |

The ranker is lexical (IDF-weighted, stemmed, with a curated + optional mined
synonym map) because the box has no GPU and forbids local ML, and no embedding
API key is configured. On adversarial slang the independent set shows the lexical
ceiling: **recall@8 ~75%** — a quarter of hard long-tail queries do NOT put the
gold tool in the ranked top-8. IDF (downweighting generic words like
group/chat/message) + light stemming moved MRR from ~0.60 baseline; further alias
mining from only 100 train queries did not generalize, so mined aliases are NOT
shipped (the loader stays for future data).

## Why that ceiling does not cause a routing regression

`find_tool` ranking is an *accelerator*, not the only path. Two guarantees make
capability equal to loading all 92:
1. `call_tool(name, ...)` invokes ANY tool by exact name — coverage is a hard 100%.
2. `find_tool(query="*")` returns the ENTIRE catalog (92 one-liners); every
   `find_tool` response also carries a hint to do so. So when the ranked top-8
   misses, the model browses everything and picks — exactly like full mode.

### End-to-end LLM routing test (the real proof)

Two identical-quality agents routed the **same 22 hard-weighted cases** (14 where
the lexical top-8 missed + 8 where it hit). `routing_answers_*.json`,
`build_routing_probe.py`:

| condition | accuracy |
|---|---|
| **FULL** — all 92 tools loaded | **21/22 (95%)** |
| **RETRIEVAL** — core + find_tool top-8 + browse | **21/22 (95%)** |

Identical score **and identical decisions** — the one miss is the same ambiguous
case in both (`get_contact_chats` vs `groups_with_member`). The retrieval agent
**browsed the full catalog on 13/22** cases: precisely where lexical recall
failed, the model recovered via browse and routed correctly. So the model routes
as well with the optimized toolset as with everything loaded — at ~56% less
always-on cost. The only real cost is one extra `find_tool` browse call on hard
long-tail queries; core/common tasks have zero overhead.

Published results also show selection accuracy *degrades* as the tool count grows
(43% → <14% in one study), so a smaller relevant candidate set is expected to help
the model, not just save tokens.

## Run

```
docker cp tests/toolsearch-eval whatsapp-mcp:/tmp/eval
docker exec whatsapp-mcp sh -c 'cd /srv && python /tmp/eval/eval.py'
```

Prints BASELINE (no aliases) vs SHIPPED (with aliases) side by side so the value
of the synonym map is visible. To test uncommitted server code without
restarting the container, `docker cp` the changed `toolsearch.py`/`server.py`
into a dir, prepend it to `sys.path`, then run `eval.py` (it appends `/srv` for
the remaining modules).
